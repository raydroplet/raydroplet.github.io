Around one year ago I wrote a web crawler in C++. It was a synchrounous one, where you provided a starting URL \<and> it crawled pages up to a specified depth while collecting their relationships. The resulting data was then passed to a graphing library to generate a visual representation of the network.

Over the past year, I've started experimenting with Rust and encountered a language similar in many aspects, but with some novel features, such as the async/await paradigm that are uncommon in C++. A rewritte of my previous crawler seemed fitting: the crate ecosystem and asynchronous model provided the building blocks for a more robust application compared to what I had created before, while allowing me do better familiarize with the novel concepts.

As explained before, a URL and depth are given and pages are crawled. The noticeable aspect here is how it is done using a recursive function: you call the `crawl_page_rec` for the root url and for all its fetched urls call the `crawl_page_rec` again for them, which call for the returned pages and so on. This is handy for the simplicity, assuming you're only interested in small networks.

> rewrite the following paragraph

This process is also _blocking_, we have to wait for the `crawl_pages` function to finish before displaying any results to the user. If the crawler does not print any messages (the ideal scenario since that's the view's work) the program would appear to be frozen until it's done.

Given our initial goal and the idea of making this process more interactive, there are a few improvements we can make:
1. instead of waiting for the final results, we could send the received urls as they come: the rendered graph would gradually increase as pages are processed
2. page fetches and parsing are sequential, we can parallelize that. 
3. the primary interface is just the command line, some graphical UI would be preferable

\<explanation of the animation>
instead of the `crawl_pages` function call, the view does something different. It sends a message to the crawler with the input information and enters a loop waiting for incoming messages. The crawler receives the message and starts internal processing, for each page it succesfully \<crawls> another message is sent to the view with the results. The view receives those messages, updates the graph and renders it.

#### Internal Events

Besides the external interface that receives commands and sends responses, we have an internal mechanism for controlling events asynchronously. Each of those executes a specific work and sends other events if adequate. `Event::Request` starts a crawl for a specified url, while `Event::Branch` takes a list of links and sends `Event::Request` for them, omitting the pages that had already been visited to avoid duplicates.

`Event::Error` and `Event::Skipped` may be sent in case a crawl is aborted, caused by an unexpected (network, parse, etc) or expected failure (duplicate pages, non html, etc). When appropriate the external responses are sent for events an external viewer cares about.

From the outside the user only needs to send requests and wait for responses, meanwhile internally the crawler is able to self organize in the way it is most suitable for processing.

The number of spawned tasks is not unbounded, there's a limit to it controlled using semaphores. At any point in time there can only a defined number of `process_page` executing.

The connector is a lightweight intermediate used to connect different actors by simply rerouting the messages. While the view and the crawler could share messages directly, having a connector allows for future extensions to the architecture.

One possible improvement is a database: Page responses would be sent both to a database for caching and the view for displaying. If a future requests ecounters an already cralwed link we could simply have the database query the contents and send them to the view, avoiding network/http requests.

> suggestion: "The connector component also exists to support future actors. One planned addition is a database actor responsible for caching pages and storing crawl history. By routing communication through the connector, the crawler can remain unaware of how persistence is implemented."

// C++ style pseudo code
class Program {
  std::vector<PageNode> nodes;
}

Program::crawl_page_rec(PageNode& page_node, int depth) {
  if (depth == 0) { return; }
  urls = get_page_urls(page_node);
  for url in urls {
    node = add_node(page_node);
    crawl_page_rec(node, depth - 1);
  }
}

Program::crawl_page(url, depth) {
  root_node = add_node(url);
  crawl_page_rec(root_node, depth);
}

int main() {
  url = request_input();
  depth = request_depth();
  page_nodes = crawl_page(url, depth);
  graph(page_nodes);
}
